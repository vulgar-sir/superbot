# 使用指南：让 Bot 真正开始干活

这份指南面向已经部署好 superbot 的用户。目标：10 分钟内跑通第一个任务，然后知道怎样写提示词，让单个 Bot、Bot 群聊或 Bot 团队把活干完。

> 英文版：[usage.md](usage.md)

## 1. 第一次使用：先配置模型

1. 用 `.env` 里的管理员账号登录。
2. 打开 **设置 → Provider → 新增 Provider**。
3. 填写 Base URL、API Key 和模型 ID，保存后点 **测试**。
4. 在模型目录里维护上下文长度、最大输出、价格，以及是否支持视觉和工具调用。价格会用于成本统计。

常见配置：

| Provider | Base URL 示例 | 模型示例 |
|---|---|---|
| DeepSeek | `https://api.deepseek.com` | `deepseek-chat`、`deepseek-reasoner` |
| OpenAI 兼容 | 服务商文档里的 `/v1` 地址 | 服务商提供的模型 ID |
| Anthropic | 使用 Anthropic Messages API 配置 | Claude 模型 ID |
| Ollama（本机） | `http://host.docker.internal:11434/v1` | `llama3.1`、`qwen2.5` 等 |

说明：

- API Key 由服务端加密存储，不会回显到前端，也不会进入 Bot 的提示词。
- 首次启动时如果还没有 Provider，可以用 `.env` 的 `SUPERBOT_DEEPSEEK_API_KEY` 种子化一个 DeepSeek Provider。
- 模型能力（视觉、工具调用、上下文长度）配置不准，会导致 Bot 行为异常。宁可填保守一些。

## 2. 创建第一个 Bot

1. 点侧栏的 **+**，输入名称、选择头像。
2. 选择默认模型；创建后点 **详情** 继续配置。
3. 在详情面板里填写：
   - **人设 / 系统提示词**：它是谁、擅长什么、按什么方式工作、哪些事不能做。
   - **工具策略**：允许使用哪些工具；高风险工具是否必须审批。
   - **工作区**：它的私有目录，文件、脚本和产物放在这里。
   - **记忆**：是否开启长期记忆；重要偏好可以固定。
   - **浏览器 / 云电脑**：需要上网或操作图形界面时再开启。

建议 **一个 Bot 只做一件事**：研究员、工程师、审查员、运营各一个，比“全能助手”可靠得多。群聊最多 6 个 Bot，通常 3–4 个 specialists 效果最好。

## 3. 三种工作方式

| 方式 | 适合什么 | 怎么用 |
|---|---|---|
| **单 Bot 房间** | 问答、写作、改代码、分析一份文件 | 进入 Bot 房间，直接发消息 |
| **群聊 / 团队** | 需要多个角色互相检查、分工、接力 | 侧栏新建群聊，选 2–6 个 Bot；用 `@BotName` 点名 |
| **例程** | 每天/每周固定重复的事 | Bot 详情或右侧面板新建例程：cron、`@every 1h` 或一次性 |
| **团队编排** | 固定流程：圆桌、流水线、Router–Worker | 团队页面创建团队，设置成员顺序、模式、最大轮次 |

群聊里，**只有被 @ 的 Bot 会说话**；如果没人被 @，主 Bot 会兜底。Bot 也可以 @ 队友，或用 `send_to_agent` 给队友发私信，主聊天只显示折叠摘要。

## 4. 提示词怎么写

### 4.1 一个好提示词的八个部分

1. **角色**：你是谁、以什么标准工作。
2. **目标**：这次要交付什么，不要只写“帮我看看”。
3. **背景**：相关文件、链接、约束、已知事实。
4. **约束**：不能做什么、必须遵守什么。
5. **工具**：允许用哪些工具；哪些操作要先问你。
6. **交付物**：格式、长度、文件位置、语言。
7. **验收标准**：怎样算完成；谁来检查。
8. **证据要求**：结论要有来源、测试输出、截图或命令结果。

再补一条 **停止条件**：什么时候停下来问你，而不是继续猜。

### 4.2 反例与正例

**不建议：**

```text
帮我调研一下 AI 手机市场。
```

**建议：**

```text
你是我的研究助理，擅长把公开信息整理成可验证的结论。

目标：调研 2026 年中国 AI 手机市场，输出一份 1500 字以内的决策摘要。

背景：
- 读者是产品负责人，关心竞争格局、关键玩家和差异化机会。
- 只使用公开可查的资料。

约束：
- 每条关键结论必须附来源链接和日期。
- 区分「事实」「推断」「未知」，不要编造数据。
- 找不到可靠来源时明确说找不到。

交付：
1. 一页摘要（不超过 10 条要点）
2. 关键玩家对比表
3. 三个机会点 + 对应风险
4. 来源清单

验收标准：每个数字都能在来源里找到；没有来源的推断必须标注。

证据：在回答末尾列出你实际打开的链接。

先给出 4 步执行计划，等我确认后再开始。
```

### 4.3 模板 1：单 Bot 研究 / 分析

```text
你是我的研究助理。目标：<要回答的问题>。
背景：<已知信息、文件、链接、读者是谁>。
约束：只使用可验证来源；区分事实/推断/未知；不要编造。
交付：<摘要 + 表格 + 风险 + 来源>。
验收：<怎样算完成>。
先给出执行计划，等我确认后再开始。
```

### 4.4 模板 2：编码任务

```text
@工程师 在 /workspace 中完成：<需求>。

先阅读相关代码，给出最小改动计划，不要直接改。
计划确认后：
- 只改必要文件，不重构无关代码。
- 运行 go test ./... 和 npm run typecheck；失败就修到通过。
- 最后贴出 diff 摘要、测试命令和真实输出。

不要执行 git push、删除数据、修改生产配置，或对外发送任何内容。
遇到需要产品决策的地方停下来问我。
```

### 4.5 模板 3：群聊协作

```text
@规划员 把目标拆成 3–5 个阶段，说明每阶段的产出和负责人。
@研究员 按阶段 1 开始执行；每条关键结论附来源。
@审查员 等研究员提交后，按验收标准给出 PASS/FAIL 和理由；FAIL 要指出回到谁。

群目标：<一句话目标>
验收标准：<可检查的条件>
证据：每个阶段结束时贴出命令输出、来源链接或截图。
```

### 4.6 模板 4：长任务 / 多轮任务

```text
这是一个长任务，预计需要多轮。

先建立检查点：目标、已完成、待办、关键决策、未决问题。
每完成一个阶段更新检查点；上下文不够时用 search_chat_history 回查原文，不要猜。
遇到需要我决策的地方停下来问我；不要为了“做完”而编造结果。
```

### 4.7 模板 5：浏览器任务

```text
@浏览器助手 打开 <网址>，完成 <只读任务>。

只做只读操作；任何提交表单、购买、发送消息、删除内容之前必须问我。
每一步截图并说明你点了什么；找不到页面元素就停下来报告，不要盲点。
```

### 4.8 模板 6：定时例程

```text
每天 09:00 汇总 <来源> 的 <内容>，输出到 <文件/房间>。

如果没有新内容，只回复“无更新”，不要为了凑字数编造。
如果抓取失败，报告失败原因和已尝试的地址。
```

### 4.9 模板 7：审查 / QA

```text
作为严格的审查者，审查 <文件/PR/方案>。

按严重程度列出问题：阻塞 / 重要 / 建议。
每个问题给出：位置（文件:行号或章节）、失败场景、修复建议。
不要直接改代码；先给审查结论和证据。
```

## 5. 怎样和 Bot 互动

- **`@BotName`**：让指定 Bot 发言；群聊里只有被点名的 Bot 会响应。
- **直接发消息**：单 Bot 房间由该 Bot 响应；群聊里由主 Bot 兜底。
- **`/side`**：旁路提问，不打断当前任务，也不写入对话记录。适合“顺便问一句”。
- **插话**：Bot 干活时发的消息会在它下一次模型调用前送达；赶不上会自动补一轮。
- **停止**：随时停止当前运行；已经产生的工具结果和检查点会保留。
- **审批**：高风险工具会弹审批卡；拒绝后 Bot 会收到结果并调整，而不是静默继续。
- **右侧面板**：查看运行状态、工具调用时间线、token 与成本、记忆和资料库。
- **群目标**：在群聊右侧设置目标与验收标准，群主 Bot 会拆阶段、分派、凭证据验收。
- **记忆**：在 Bot 详情里查看、置顶、归档或删除记忆；重要偏好可以直接说“记住……”。
- **资料库**：页面、文档、文件和媒体会自动收录；也可以让 Bot 主动写入。

## 6. 安全使用

- **不要把 API Key 写进提示词**。用 Provider 配置；需要登录信息时用 **保险库（Vault）**。
- **高风险操作要审批**：删除、支付、对外发送、修改生产配置、执行不熟悉的 shell 命令。
- **本地设备**：`superbot device` 的每条 shell 命令都要你原生批准；看不懂的命令不要批准。
- **验证输出**：要求 Bot 给出来源、测试输出或截图。AI 的自信不等于正确。
- **生产环境用 HTTPS**，并把 `SUPERBOT_COOKIE_INSECURE` / `SUPERBOT_ALLOW_INSECURE_COOKIE` 设为 `false`。
- **多租户**：superbot 面向可信团队；不要让陌生人共用管理员账号。需要隔离时跑独立实例。

## 7. 常见问题

| 现象 | 先检查什么 |
|---|---|
| Bot 不回复 | Provider 是否配置、模型 ID 是否正确、额度是否用完；右侧面板的错误信息 |
| 工具不可用 | 工具策略、审批是否被拒绝、沙箱镜像是否构建、容器能否联网 |
| 回答太长 / 太短 | 在提示词里给字数、格式和“不要写什么” |
| 群聊没人说话 | 是否 @ 了至少一个 Bot；群成员是否为空；主 Bot 是否可用 |
| 记忆不准 | 打开记忆面板，删除错误记忆；重要偏好直接让 Bot 记住 |
| 任务中断 | 检查 worker 状态；从检查点续跑；必要时重新发任务 |
| 浏览器操作失败 | 电脑是否启动、页面是否加载、是否需要登录；让 Bot 截图并报告 |
| 成本太高 | 换小模型、限制上下文、让 Bot 先给计划再执行、给输出长度上限 |

## 8. 完整例子：三个 Bot 做一份调研报告

**创建三个 Bot：**

- **规划员**：擅长拆解目标、定义验收标准。
- **研究员**：擅长查资料、附来源、区分事实与推断。
- **审查员**：擅长挑错、检查证据链、给 PASS/FAIL。

**创建群聊**，选这三个 Bot，然后发：

```text
群目标：产出一份 1500 字以内的《2026 中国 AI 手机市场》决策摘要。

@规划员 先拆成 4 个阶段，说明每阶段产出和负责人，等我确认后再开始。
@研究员 阶段 1 先收集公开资料，每条结论附来源链接和日期。
@审查员 等研究员提交后，按“每个数字都有来源、事实/推断分开”的标准给 PASS/FAIL。

验收标准：
1. 10 条以内的关键结论；
2. 关键玩家对比表；
3. 三个机会点 + 风险；
4. 来源清单；
5. 没有来源的数字必须标注为推断或删除。

每阶段结束贴出证据；FAIL 要指出回到谁、改什么。
```

**接下来会发生什么：**

1. 规划员拆阶段，研究员按阶段执行，审查员检查。
2. Bot 之间可以 `@` 队友，或用 `send_to_agent` 私信，不刷屏。
3. 审查员给 PASS/FAIL；FAIL 的阶段回到对应成员重做。
4. 最终报告写入资料库；你可以在右侧面板查看工具调用和成本。
5. 如果结果满意，可以把这套流程保存为团队模板或例程，下次直接复用。
